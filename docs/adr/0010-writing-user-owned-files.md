# 写入用户拥有的文件须经唯一入口与三重保护

截至 ADR 0008，本应用的性格是只读扫描器加可重建缓存：sqlite、价目、官方额度捕获文件都在应用自己的数据目录里，丢了可以重建。ADR 0009 引入全局指令后，应用第一次要改用户主目录里、由用户自己维护、属于其它 Source 的文件。这些文件不可重建。用户的全局指令平均数月才更新一次，被错误覆盖后不会立刻发现。

本 ADR 不讨论「全局指令」这个维度本身（见 ADR 0009）。它只定一条会被反复引用的约束：**凡写入用户拥有的、不属于本应用数据目录的文件，必须走唯一入口，并满足下列强制要求。** 维度边界写完基本不动；本约束会被后续每个想写文件的功能引用与修订。合在一起，查阅「能不能写文件」的人要读一整篇讲维度的文档，所以拆开。

**决定**：全应用只允许一个写入此类文件的入口。入口之外任何位置都不得直接写用户主目录。每一次写入必须同时满足：

1. **写入前 mtime 校验**：打开文件时记录 mtime；保存前重新 `stat`。不一致则拒绝写入，原文件保持不变，并提示该文件在外部被修改过。不做三方合并，也不展示 diff。
2. **写入前备份原文件**：备份落到应用数据目录下的独立备份目录，按被写文件保留最近若干份。备份失败则中止写入。
3. **原子写**：先写入同目录临时文件；替换既有文件时再 `rename` 到目标路径，仅创建新导出时以原子且 no-replace 的方式发布。任何中断都不得留下半截目标文件，也不得覆盖竞态中出现的新目标。

路径受显式白名单约束，不在名单上的路径一律拒绝。持久白名单只收本应用明确负责编辑的、由用户手写的指令或配置文件；由原生保存对话框返回的一次性导出目标可作为临时白名单，但只允许本应用生成的已声明导出格式。

**禁止写入**，即使未来有人觉得「顺手清一下」：

- 第三方应用的数据库，包括但不限于 Cursor 的 `state.vscdb`、其它工具的 sqlite / leveldb / cookies。
- 机器生成的记忆或缓存（Claude 自动记忆目录、Cursor `pendingMemories` 所在库）。
- 本应用自己的 `usage.sqlite`、价目、官方额度缓存——这些继续走既有模块，不经过本入口，也不适用本 ADR。

**理由**：这个应用存在的理由之一是对抗用户健忘。把数据安全押在「用户会记得别同时开两边」上，和这个理由矛盾。mtime 校验挡最常见的覆盖；写前备份挡其余情况；唯一入口保证这两道保险不会被第二个 `fs::write` 绕过。

## Consequences

- 第一个遵守本 ADR 的功能是全局指令编辑。新增任何「写用户文件」的能力，必须先扩白名单，并说明为何该路径是用户手写、本应用有权改。
- 对话导出仅允许原子创建用户刚刚通过原生保存对话框确认的 `.md` 或 `.jsonl` 新目标；目标已存在或在确认后被创建时一律拒绝，因此不触发原文件备份，也不产生对话正文的自动备份。该临时授权不构成任意文件编辑能力。
- 白名单随 Source 版本变化；扩名单是显式决策，不是实现细节。
- 2026-08-23：扩 `~/.grok/` 下 Grok 官方候选指令文件名（`AGENTS.md` / `Agents.md` / `AGENT.md` / `CLAUDE.md` / `Claude.md` / `CLAUDE.local.md`）。这些是用户手写全局指令，本应用已扫描展示，编辑权与 Claude / Codex / Gemini 同源。不包含 `config.toml`、`sessions`、`auth.json`。
- 同日再扩 `~/.grok/rules/*.md`。Grok 会加载该目录下的 markdown，与候选文件名同源、用户手写。可写标志由 `is_allowed` 在扫描时写入 DTO，前端不再维护第二份路径表。
- mtime 校验挡不住并发写，只挡「打开后外部已改、再保存覆盖」。
- 备份目录会增长；按文件保留最近若干份，不进 git，不进本机用量备份包的语义（除非后续修订本 ADR）。
- 只读打开、跳到外部编辑器，不属于本 ADR 的写入，不受白名单限制。
