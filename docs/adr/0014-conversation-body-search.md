# 对话目录搜索正文

ADR 0011 把事件正文放进 `conversation_events`，只为按页读取详情。目录搜索仍是对标题、来源、项目、模型、会话 ID、时间的 `LIKE %…%`。问「哪次改了 auth」必须打开详情。索引费已经交了，正文搜索是这块派生缓存的正当用途。

**决定**：对 `conversation_events.text` 与 `name` 建 FTS5（trigram）派生索引。目录同一个搜索框：标题命中排前面，正文命中随后列出；点正文命中滚到该会话第一条匹配事件并高亮片段。搜的是提问 / 回复 / 工具名与输出，不搜附件二进制，也不搜 `details`。未建完索引的会话标明「正文索引未就绪，当前只搜标题」，补建进度可见，不假装全库可搜。

短于 3 个字符的查询只走标题（trigram 无法加速）。不在这里补齐尚未适配的事件种类。不做跨会话语义搜索 / embedding。

备份仍不携带 `conversation_events` 与 FTS 表，并清空 `event_index_generation`。正文不进 MCP、不上传。重建缓存后可以重建 FTS。设置页展示对话索引占用，并写清搜索读本机正文、数据仍留在本机。

## 修订：倒排不存位置（`detail=none`）

原先按 FTS5 默认的 `detail=full` 建表，倒排里为每个三元组的每一次出现存了位置偏移。这块从没被读过：排序键 `match_rank` 是手写的 0/1，片段由 Rust 的 `excerpt()` 从正文切，没有用 `bm25()` / `snippet()`。真实库里它是整个缓存最大的一项——106 万事件、400 MB 正文，倒排 2.73 GB，占 4.3 GB 库的六成。

**改为 `detail=none, columnsize=0`。** 在这份真实库上实测倒排 2.73 GB → 294 MB，整库 VACUUM 后 4.3 GB → 1.7 GB；检索反而快一倍（posting list 小了，扫得少）。迁移本身约 65 秒，随后的一次性 VACUUM 约 17 秒。

代价是 FTS5 不再接受短语查询。目录搜索改为：把关键词按字符切成 3 字窗口、每个窗口单独加引号用 `AND` 连接发给 FTS5，再回表 `LIKE` 复核。窗口交给 FTS5 自己 tokenize，大小写折叠仍由它决定，Rust 不复刻。召回是子串语义的超集（实测假阳性约 2%），复核后结果与原先逐条一致。这个查询形态在 `detail=full` 上同样成立，所以迁移不需要两套代码。

迁移在后台线程做（`lib.rs::spawn_conversation_fts_migration`），与预聚合补建同一套路：百万行重建要几十秒，放启动路径里会像卡死。迁移期间旧表继续服务查询，不需要「未就绪」状态。判据是建表语句里有没有 `detail=`。

原先留的「不索引正文的瘦身开关可后做」**作废**：那是在「正文索引就得花 2.4 GB」的前提下写的补偿措施。前提没了，就不该把这个选择推给用户。

搜索质量上仍有一处已知缺口：短于 3 个字符的查询只走标题，而中文双字词（「登录」「重构」「鉴权」）正好落在这条线下，是静默降级。trigram 结构上查不了 2 字符，这里不解决。
