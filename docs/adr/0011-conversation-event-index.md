# 对话事件正文进入本地索引

截至 ADR 0003，本应用的性格是：消耗记录进可重建的 sqlite 缓存，对话正文只留在各 Source 的源文件里。打开会话时现场解析源文件，目录索引只存会话行和父子关系摘要。这条原则挡住了「把用户的对话全文写进库」——备份、设置页的「重建缓存」、以及「缓存丢了可以再扫一遍」都建立在「库里没有正文」之上。

会话详情分页把这条原则推翻了。一条本机最大的 Codex 会话：源文件 114 MB，解析出约 8 万条事件，整份序列化超过 150 MB。继续「正文只留在源文件」意味着每次打开、每次跟随、每次点「加载全文」都把整份文件重新解析一遍。要按页读取，就必须在摄取时把归一化后的事件写进本地索引。

**决定**：对话事件的正文进入 `usage.sqlite` 的事件索引表。每条存 `text`、种类、参与者、时间、附件元数据和能力/内容状态，**不存** `details`。`details` 实测是正文的两倍体积，却只在用户展开折叠块时才看。索引是纯派生缓存：源文件仍是权威，库可以删掉后按可信摄取语义重建。

本决定只改缓存里装什么，不改「谁的文件能写」：

- **ADR 0003（可信摄取）**：仍然适用。某会话有源文件解析失败时，该会话保留上一代索引，不用残缺结果覆盖。索引行带 `index_generation` 代次标记；全部源文件都无阻塞性问题之后，才把该会话的上一代删掉。
- **ADR 0010（写用户文件）**：不适用。事件索引写的是本应用自己的 `usage.sqlite`，不是用户主目录里由其它 Source 维护的文件。对话正文不会因为进了索引就被写回源文件，也不会进入用户拥有的任何路径。

备份产物不携带 `conversation_events` 表，并清空 `event_index_generation`。事件索引是纯派生缓存，恢复后由 `open_db` 建空表、再由渐进补建重建；回退路径保证补建期间详情仍可用。备份因此仍只装消耗记录与短标题，不含对话正文。

## Consequences

- 数据库体积会明显上升（本机全量约从 125 MB 到 1 GB 量级）。这是按页读取必须付的代价。
- 递增对话适配器版本会使既有索引按会话失效；启动摄取不再因此重解析全部源文件，改由后台按 `ended_at` 倒序补建。`adapter_version = 0` 仍是「重建缓存」的强制重解析哨兵。
- 详情读取按会话就绪分流：已索引走索引（不带 `details`），未索引回退整份解析；回退路径长期保留，因此索引出错时有降级开关。
- 目录索引继续只留会话行和父子关系，不在扫描阶段囤积整份 `ParsedConversation`。

## 对话记录适配来源（2026-09）

`conversation::CONVERSATION_ADAPTERS` 覆盖 **13 个** Usage Source：codex、claude、cursor_agent、dsh、factory、kimi、grok、pi、omp、gemini、opencode、qwen、copilot。**未覆盖**：hermes。索引版本哨兵为 **`CONVERSATION_ADAPTER_VERSION`**（独立于 `store::ADAPTER_VERSION`）；纯重构不得改动，改动意味着事件归一化输出变了。
