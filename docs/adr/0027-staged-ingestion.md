# 摄取分段：用量先提交、对话目录后台、事件按需补建

启动摄取原来是一个事务、一把写锁：21 个来源的消耗记录、Cursor 会话、21 个来源的对话记录目录（变化的会话文件整份解析，写事件和正文倒排）、预聚合，全部跑完才提交。用户最关心的消耗记录数字，要等对话记录的事件和倒排写完才出来。侧边栏长时间停在「正在同步 · 启动摄取中…」，点刷新也没反应。

启动时拉起的事件补建、对话派生缓存迁移、正文倒排维护又和启动摄取抢同一把写锁。抢不到锁时界面照样显示「启动摄取中…」，看起来像卡死。

**决定**：摄取按用户需要的先后拆成三段。

1. **用量阶段（同步）**：清理未知来源、全部来源的消耗记录、Cursor 会话、预聚合，一个事务提交后立即返回报告（`ingest::ingest_usage`）。报告里没有对话记录问题，`partial_success` 也不看对话记录。「启动摄取中…」到这里结束。
2. **对话目录阶段（后台）**：`ingest::refresh_conversation_catalogs` 按 `CONVERSATION_SOURCES` 逐个来源处理，每个来源单独拿写锁、单独开事务、处理完立即提交并释放锁，再处理下一个。期间通过进度事件告诉前端「对话目录同步中 N/M」，结束时带出本轮问题数。全局单飞：在跑时再触发只记一次「补跑」，本轮结束后再跑一轮。
3. **事件补建（后台，渐进）**：复用 ADR 0011 的事件索引补建。目录阶段只保证会话行新，事件交给补建。

## 待补建

目录阶段对「需要整份解析」的会话，照常解析出摘要，写会话行和会话文件清单，但**不写事件、不写倒排、不动 `event_index_generation`**，并把 `conversation_sessions.event_index_dirty` 置 1（`conversation::refresh_catalog`）。旧一代事件原样留着。

- 会话文件上的「目录已见指纹」（mtime、大小、修订号、适配器版本）照常推进，事件游标（已索引字节偏移、行号、最大序号）不推进。源文件不再变化时，下一轮目录同步直接跳过，不反复整份解析。
- 能走后缀增量、且不是待补建的会话（Codex、Claude）在目录阶段直接追加，成本低，追加后仍就绪。已是待补建的会话不走增量，留给补建整份重建。
- 事件**就绪**统一为：`adapter_version = CONVERSATION_ADAPTER_VERSION`，`event_index_generation` 非空，且 `event_index_dirty = 0`。详情走不走索引、推送走不走索引、补建进度、目录行的已索引标志都用这一条。
- 正文搜索与按工具名筛选仍按会话当前的 `event_index_generation` 连接事件，所以待补建会话暂时命中旧一代内容，不会凭空消失。
- 补建成功后清掉标记。补建先取优先队列里的会话，再按 `ended_at` 倒序取未就绪会话（`backfill_event_index_step_prioritized`）。用户打开一个未就绪会话时，详情照常走整份解析回退，同时把它插到队列最前面。

「待补建」是一个显式标记，不靠删事件或改适配器版本号表达。这样旧一代能继续服务搜索和筛选，中途退出后下次启动也能接着补。

## 调用方

- 主窗口的摄取命令、托盘的 stale 刷新：先同步跑用量阶段，再在后台跑目录阶段。目录阶段结束后拉起事件补建（同样单飞）和正文倒排维护。
- 补建线程全局单飞。用户打开事件未就绪的会话时（`get_conversation_detail`、`get_conversation_events`），命令把它插到补建优先队列最前并确保线程在跑；已就绪或补建失败的会话会从队列里清掉。线程每步重新读队列，所以新请求在下一个会话就生效。
- 目录阶段的最近一次问题列表存在 `AppState`，由命令 `get_conversation_catalog_issues` 读取。整轮失败（拿不到写锁、线程异常）记成一条 `source` 为空的问题，并照常发出结束事件，界面不会停在「同步中」。
- 自动推送的本机刷新：同步跑完用量和目录两段（`ingest_all_with_mode`，目录走待补建），不等事件补建。结束后只是拉起事件补建线程，不等它。推送读正文时对未就绪会话走整份解析回退。
- `ingest_all` 保留两段串行、目录整份写事件的组合语义，供性能探测和测试使用，结果与拆分前一致。
- 「重建缓存」不分段：用户显式发起，一次性同步完成消耗记录、Cursor 会话、对话目录和事件。
- 启动时预聚合补建和自动推送调度照旧在 `setup` 拉起。事件补建、对话派生缓存迁移、正文倒排维护改为首次用量阶段完成后拉起；启动 60 秒内没有发生用量阶段（例如只开托盘）也拉起，取先到者，只触发一次。

## 与既有 ADR 的关系

- **ADR 0003（可信摄取）**：仍然适用，粒度不变。消耗记录仍是逐文件「最后一次正确结果」、失败不对账。目录阶段每个来源一个事务：某个来源失败只回滚这个来源，保留它上次的目录，其他来源照常提交，不留半截状态。待补建只是推迟写事件，不用残缺结果覆盖旧一代。
- **ADR 0011（对话事件索引）**：修订两处。启动摄取不再同步写事件，整份解析的会话由补建重建；就绪定义加上 `event_index_dirty = 0`。代次语义、回退路径、备份清空 `event_index_generation` 不变；备份产物另把 `event_index_dirty` 置 0，恢复后所有会话照常进入补建。
- **ADR 0024（对话缓存维护）**：小步合并原来挂在「每轮摄取提交后」。现在目录阶段逐源提交，倒排的有上限 `merge` 在全部来源结束后做一次，补建结束时照旧。
- **ADR 0025（正文按位置引用）**：不受影响。外置正文只在写事件时决定，待补建会话要等补建写事件时才外置。

## Considered Options

- **只把对话目录挪到后台、仍整份写事件**：一个大会话就能占住写锁几十秒，「刷新」照样被挡住。逐源提交加待补建，刷新最多等当前那个来源。
- **用删事件或把 `adapter_version` 置 0 表达待补建**：补建前搜索和工具筛选会变空，且和「重建缓存」的强制重解析哨兵混在一起。
- **各来源并行处理**：写锁只有一把，并行也是排队，不在本次范围。

## Consequences

- 首页数字在用量阶段提交后即可用；对话记录页在目录阶段结束前显示上一次的目录。
- 目录阶段结束前，用量阶段的报告里没有对话记录问题；问题数由进度事件的结束消息带出，最近一次的列表供设置页诊断读取。
- 待补建会话在补建前，搜索和工具筛选结果暂时偏旧，补建进度把它算进未完成数。
- 性能探测分别输出用量阶段和对话目录阶段的耗时。
- 消耗记录对追加型日志的增量解析、对话适配器的「只解析摘要」模式不在本决定里，另行决策。
