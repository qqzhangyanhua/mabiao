# 对话派生缓存的持续维护

ADR 0014 修订把正文倒排换成 `detail=none` 后，真实库倒排是 294 MB。那是迁移当天整份重灌出来的状态，不是稳态。一个月后同一台机器上：469 MB 正文配 3.17 GB 倒排、1.2 GB 空闲页，整库 6.04 GB；在副本上做一次 `optimize` + `VACUUM` 回到 2.24 GB。膨胀不是「对话太多」，是缓存从不整理：

- 13 个对话记录适配器里只有 Codex 走后缀增量，其余来源的会话文件只要变了就整会话换代（ADR 0011 的代次语义）。托盘每 5 分钟摄取一次，活跃会话每轮都被整份重写。
- 换代时每条事件对倒排写约四次：新代插入；`finalize_session_events` 逐行改 `sequence`，而 `AFTER UPDATE` 触发器不看改的是哪一列，于是倒排先删后插；旧代删除再记一次。
- 外置 content 的 FTS5 删除只是往新段里追加删除标记，旧段里的数据要等合并到最老的段才真正消失。代码从没调过 `merge` / `optimize`；后台补建按语句自动提交，又制造了大量小段。
- `auto_vacuum` 是关的，腾出的页只进 freelist，文件不变小。

**决定**：倒排与库文件的体积由应用自己维护，不推给用户。

1. **倒排只跟正文走。** 更新触发器收窄为 `AFTER UPDATE OF text, name`。重排 `sequence` 不再碰倒排，换代写入量约减半。只改触发器、不改事件内容，因此不递增 `CONVERSATION_ADAPTER_VERSION`；判据是触发器定义里有没有 `UPDATE OF`。
2. **每轮小步合并。** 每轮摄取提交后、以及后台补建结束时，在同一把写锁下跑一次有上限的 `('merge', N)`，N 以单次耗时可控为准。补建的每个会话包进一个事务，新代写入与旧代删除一起生效，也不再逐语句产生小段。
3. **按删除量兜底全量整理。** 删除触发器同时给单行维护表的 `deleted_since_optimize` 加一；每次全量 `optimize` 后清零并记下当时的事件行数。`deleted_since_optimize ≥ max(上次行数 × 50%, 100,000)` 时，后台线程拿写锁做一次全量 `optimize`。没有维护记录的库（老库升级、从备份恢复）视为需要整理，所以不另写一次性迁移。
4. **按空闲页回收磁盘。** 只在全量整理之后看 `freelist_count` / `page_count`：空闲 ≥ 1 GB 且 ≥ 30% 时 `VACUUM`。不预检剩余磁盘空间；写满时 SQLite 报 `SQLITE_FULL` 并回滚，只记日志，下次整理后再试。

维护表与事件索引同属派生缓存：备份不携带，恢复后按「无记录」处理。界面不新增状态，设置页既有的「对话索引占用」自然反映结果。

## Considered Options

- **不存正文的瘦身开关**：ADR 0014 已作废，这里维持。膨胀来自缺维护，不是功能本身太重；推给用户既丢搜索又丢分页。
- **用 `dbstat` 测倒排 / 正文比例做阈值**：冷缓存下真实库要 31 秒，不能挂在摄取路径上。
- **调大 FTS5 `automerge` / `crisismerge`**：只改合并时机，删除标记仍要等合并到最老段；且合并落在哪次写入上不可预期。
- **`auto_vacuum=INCREMENTAL`**：要先整库转换一次，之后页面更碎；持续合并之后空闲页本就少，按阈值 `VACUUM` 足够。

## Consequences

- 首次升级的大库会在后台锁写数分钟（真实库 `optimize` 约 3 分钟、`VACUUM` 约 1.5 分钟），期间摄取排队、查询读旧快照，与 ADR 0011 / 0014 的形态迁移同一套路。
- 设置页的「对话索引占用」改为读维护表里上次实测的值，不再每次刷新都跑 `dbstat`（真实库冷缓存 31 秒）。实测在全量整理、补建结束后由后台线程做。
- 让更多追加型来源走后缀增量（首先是 Claude）能从源头减少换代，单独决策；本 ADR 只保证无论换代多频繁，体积都收敛。
- Gemini、Copilot 原地重写 JSON，OpenCode 存 SQLite，天生只能整会话换代，长期依赖第 2、3 条。
